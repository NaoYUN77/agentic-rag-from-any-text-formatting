# 问题 02: 块粒度不均

**优先级: P0**　**状态: 待解决**

## 现象

同一次分块, 块大小跨度很大:

```text
24 个 chunk   字数 min=431   均值=713   max=2138
```

数据来源: `pipeline/experiments/10_pipeline_full.txt`

**块大小的理论范围是可以算出来的:**

```text
max_chars = 800, window_chars = 400
理论下限 = max_chars - window_chars = 400
理论上限 = max_chars = 800
实测     431 ~ 2138 (上限被超长单句突破)
```

## 根因

### 根因 A: 长度约束只有单边

```python
while end < n and (size + len(sents[end]) <= max_chars or end == start):
    size += len(sents[end])
    end += 1
                     ↑ 只有上限判断, 没有下限
```

**`or end == start` 这个保护条件, 本意是防止死循环**(万一单句超过 max_chars), **副作用是放行了超长单句**:

```text
目录页 2138 字, 中间没有一个 。
  ↓ 分句后它是一"句"
  ↓ 800 + 2138 > 800, 但 end == start 强制吃下
块 = 2138 字
```

### 根因 B: 边界窗口让切点能往前挪

```text
从 start 吃满到 end(≈800 字)
  ↓ 切点可以在 [end-400, end] 里挪
  ↓ 如果切点挪到 end-400, 这块只剩 400 字
```

**这就是 431 那个最小值的来源。**

### 根因 C(更本质): 语义断点的分布天然不均匀

```text
某些位置连续几个都是高距离      -> 块被切得很碎
某些位置几十句都很平缓          -> 没有断点可用, 只能硬切
```

**长度约束只能"限制范围", 不能"重新分配断点"。** 想真正均匀, 得允许"该切的地方不切"或"不该切的地方硬切" —— 但那又破坏了语义。

## 影响

```text
块太大(2138)   向量被稀释, 查询只能匹配到"平均印象"
块太小(431)    信息量不够, 召回后还要拼好几块才能回答
粒度不齐       检索结果的可比性下降 —— 同样是 top-1,
              有的块包含完整答案, 有的只有半句话
```

## 解决方向

### 方向 1: 加 min_chars 下限(最简单)

在挑切点前先检查: 如果切出来的块小于 min_chars, 就不切, 和后面合并。

`pipeline/hybrid_chunk_demo.py` 里的 `semantic_first_chunks()` 已经有这个逻辑, 但 `pipeline/rag_pipeline.py` 用的 `chunk_by_window()` 没有。

**成本: 十几行代码。**

### 方向 2: 超长单句做字符级兜底

```python
if len(sent) > max_chars:
    # 按字符或按更细的分隔符(换行/逗号)再切
    parts = [sent[i:i+max_chars] for i in range(0, len(sent), max_chars)]
```

**注意: 这是"物理兜底", 不解决语义。** 但至少保证块大小可控。

### 方向 3: 换成"语义优先 + 长度双向约束"

`pipeline/hybrid_chunk_demo.py` 里的策略 4:

```text
先找出所有语义断点
  -> 太长就补切, 太短就合并
```

**实测它能把块数从 22 涨到 28, min 从 357 降到 131** —— 说明它并没有让块更均匀, 只是切得更碎。**这个方向需要再调参。**

## 待验证

```text
[ ] min_chars 设多少合适? 和 max_chars 的比例?
[ ] 超长单句用字符硬切, 还是用更细的分隔符(逗号/换行)?
[ ] 块大小均匀本身是不是一个值得追求的目标?
    (可能"语义完整但大小不均"比"大小均匀但语义被切碎"更好)
```
