# 问题 02: 块粒度不均

**优先级: P0**　**状态: 上限已解决；下限经实测「不值得修」（2026-09-22）**

> ⚠️ 本文「现象」「根因」写于旧 LlamaIndex 管线（带 `max_chars` / `window_chars`）。
> 那两个根因——窗口挪切点、双边约束——在当前固定大小切块器里**已不存在**。
> 当前状态见下一节。

## 2026-09-22: 上限守住了，下限经实测不值得修

### 当前分布（`rebuilt_capped`，113 chunks）

```text
token:  min=11   p25=131   p50=206   p75=459   p90=738   max=794
        > 800 的 chunk:  0 个 (0.0%)   ← 上限守住了
        < 100 的 chunk: 18 个 (15.9%)  ← 下限仍然单边
```

原文「超长单句突破上限」已不复现（当前切块器对 `piece.is_atomic and piece.oversized`
会单独成块）。但**下限确实没有约束**，最小的块只有 11 token。

那 18 个 tiny chunk 分两类：

```text
作者署名行   "Written by Erik S. and Barry Zhang. ..."      6 个
短引言       "In this section, we'll explore ..."            其余
```

### 关键实测：它们确实在挤占位置

| 阶段 | top-5 位置数 | tiny(<100tok) 占比 |
|---|---:|---:|
| dense | 195 | **19 个 (9.7%)** |
| sparse | 152 | 9 个 (5.9%) |
| rrf | 195 | 13 个 (6.7%) |

**dense 的 top-5 里有近 1/10 被 tiny chunk 占着。** 看起来是个真问题。

### 但模拟显示：过滤掉它们几乎没收益

用现有评估数据模拟「把 tiny 从结果里过滤掉」（只用 `per_query` 的 top-10，
所以 MRR 算到 @10）：

| 阶段 | 阈值 | hit@5 | MRR@10 |
|---|---|---|---|
| dense | ≥100 | 0.941 → 0.941（不变） | 0.803 → **0.812** (+0.009) |
| sparse | ≥100 | 0.929 → 0.929（不变） | 0.767 → **0.753** (−0.014) |
| **rrf**（生产路径） | ≥100 | **0.971 → 0.971（不变）** | 0.801 → **0.809** (+0.008) |

**结论：不值得修。** 三点理由：

1. **hit@5 完全不变** —— tiny chunk 占的位置本来也不会是 gold
2. **rrf 只 +0.008 MRR@10**，n=34 下在噪声内
3. **sparse 反而变差 −0.014** —— 过滤不是无代价的

### 一个值得记住的判据：**占位 ≠ 有害**

tiny chunk 占了近 10% 的 top-5 位置，指标却几乎不动。
原因是它们**没有和 gold 竞争** —— 占的是本来就会空着的位置。

**"某个东西占了结果的位置"不等于"它挤掉了有用的东西"** ——
要判断危害，得看**相对 gold 的排名**，而不是看它在结果里的占比。

### 若要修，代价不小

真正需要的是「最小块约束」，而它有个硬约束：**不能跨章节合并**
（那会重新引入 issue 06「块跨章节」）。所以只能在**同一 parent 分组内**
把短块与前一个兄弟合并 —— 要重建 chunk（fragments / text / metadata 都要重算），
改动量明显大于 parent 分组那类修复。**收益 +0.008 撑不起这个复杂度。**

## 现象

同一次分块, 块大小跨度很大:

```text
24 个 chunk   字数 min=431   均值=713   max=2138
```

数据来源: `pipeline/experiments/10_pipeline_full.txt`

**块大小的理论范围是可以算出来的:**

```text
max_chars = 800, window_chars = 400
理论下限 = max_chars - window_chars = 400
理论上限 = max_chars = 800
实测     431 ~ 2138 (上限被超长单句突破)
```

## 根因

### 根因 A: 长度约束只有单边

```python
while end < n and (size + len(sents[end]) <= max_chars or end == start):
    size += len(sents[end])
    end += 1
                     ↑ 只有上限判断, 没有下限
```

**`or end == start` 这个保护条件, 本意是防止死循环**(万一单句超过 max_chars), **副作用是放行了超长单句**:

```text
目录页 2138 字, 中间没有一个 。
  ↓ 分句后它是一"句"
  ↓ 800 + 2138 > 800, 但 end == start 强制吃下
块 = 2138 字
```

### 根因 B: 边界窗口让切点能往前挪

```text
从 start 吃满到 end(≈800 字)
  ↓ 切点可以在 [end-400, end] 里挪
  ↓ 如果切点挪到 end-400, 这块只剩 400 字
```

**这就是 431 那个最小值的来源。**

### 根因 C(更本质): 语义断点的分布天然不均匀

```text
某些位置连续几个都是高距离      -> 块被切得很碎
某些位置几十句都很平缓          -> 没有断点可用, 只能硬切
```

**长度约束只能"限制范围", 不能"重新分配断点"。** 想真正均匀, 得允许"该切的地方不切"或"不该切的地方硬切" —— 但那又破坏了语义。

## 影响

```text
块太大(2138)   向量被稀释, 查询只能匹配到"平均印象"
块太小(431)    信息量不够, 召回后还要拼好几块才能回答
粒度不齐       检索结果的可比性下降 —— 同样是 top-1,
              有的块包含完整答案, 有的只有半句话
```

## 解决方向

### 方向 1: 加 min_chars 下限(最简单)

在挑切点前先检查: 如果切出来的块小于 min_chars, 就不切, 和后面合并。

`pipeline/hybrid_chunk_demo.py` 里的 `semantic_first_chunks()` 已经有这个逻辑, 但 `pipeline/rag_pipeline.py` 用的 `chunk_by_window()` 没有。

**成本: 十几行代码。**

### 方向 2: 超长单句做字符级兜底

```python
if len(sent) > max_chars:
    # 按字符或按更细的分隔符(换行/逗号)再切
    parts = [sent[i:i+max_chars] for i in range(0, len(sent), max_chars)]
```

**注意: 这是"物理兜底", 不解决语义。** 但至少保证块大小可控。

### 方向 3: 换成"语义优先 + 长度双向约束"

`pipeline/hybrid_chunk_demo.py` 里的策略 4:

```text
先找出所有语义断点
  -> 太长就补切, 太短就合并
```

**实测它能把块数从 22 涨到 28, min 从 357 降到 131** —— 说明它并没有让块更均匀, 只是切得更碎。**这个方向需要再调参。**

## 待验证

```text
[ ] min_chars 设多少合适? 和 max_chars 的比例?
[ ] 超长单句用字符硬切, 还是用更细的分隔符(逗号/换行)?
[ ] 块大小均匀本身是不是一个值得追求的目标?
    (可能"语义完整但大小不均"比"大小均匀但语义被切碎"更好)
```
