# 语义分块策略对比(工程经验)

> 本文档是**选型导向**的: 把几种分块策略和嵌入机制放在一起横向对比, 给出成本、效果和适用场景。
>
> 与其它文档的关系:
> - 原理与推导 -> `rag_chunking_concepts.md`
> - 单次实验的档案 -> `pipeline/experiments/findings/`
> - 原始数据 -> `pipeline/experiments/`
>
> 所有数字来自真实运行, 语料为 `pipeline/corpus/redhat_p1-20.md`(274 句 / 17123 字),
> 嵌入模型为阿里云百炼 `qwen3-vl-embedding`(1024 维)。

---

## 一、先看清全貌: 两个独立维度

分块这件事容易混, 是因为它其实有**两个独立的决策**:

```text
维度一: 怎么切           切点怎么定
                        纯固定 / 纯语义 / 长度+语义 / 语义+长度 / 句子窗口

维度二: 嵌什么           送去嵌入的是什么文本
                        单句 / 窗口 / 单句+metadata
```

**两个维度可以自由组合**, 而且不同组合的成本差别很大。分开看就清楚了。

```text
                    ┌─────────────────────────────────────┐
                    │  维度二: 嵌什么                      │
                    ├──────────┬──────────┬───────────────┤
                    │  单句     │  窗口     │  单句+metadata │
    ┌───────────────┼──────────┼──────────┼───────────────┤
    │ 纯固定长度     │          │          │               │
    │ 纯语义分块     │          │  ✔ 必须   │               │
    │ 长度+语义微调  │  ✔ 常用   │  可选     │  不推荐        │
    │ 语义+长度约束  │  ✔ 常用   │  可选     │  不推荐        │
    │ 句子窗口       │  ✔ 必须   │  可选     │  不推荐        │
    └───────────────┴──────────┴──────────┴───────────────┘
```

**关键约束: 纯语义分块必须用窗口嵌入** —— 因为它的判据就是"相邻窗口的语义距离", 不拼窗口就算不出来。

## 二、五种分块策略

### 策略 1: 纯固定长度

```text
做法    到 max_chars 就切, 不看语义
代表    OpenAI 的默认(800 token 块 + 400 token 重叠)
```

**实测(274 句, max_chars=800):**

```text
块数 21   字数 min 438 / 均值 815 / max 2138
切点均值距离 0.3628    (全局均值 0.3612, 相对 1.00x)
```

**切点距离几乎等于全局均值 —— 纯固定长度的切点在语义上是随机的。**

这是数学必然: 随机位置的平均距离期望就是全局均值。**不是"效果差", 是"没有语义偏好"。**

**适用**: 快速原型、对精度要求不高的场景、配合高重叠使用。

### 策略 2: 纯语义分块

```text
做法    分句 -> 每句配窗口 -> 嵌入 -> 算相邻距离 -> 统计阈值找断点 -> 成块
代表    LangChain SemanticChunker / LlamaIndex SemanticSplitterNodeParser
```

**实测(274 句, buffer_size=1, percentile 95):**

```text
块数 15   字数 min 50 / 均值 1158 / max 4426
```

**最大的问题是块大小失控:**

```text
amount=50  -> 137 个 chunk   字数 min=6     max=2901
amount=90  ->  29 个 chunk   字数 min=36    max=3304
amount=95  ->  15 个 chunk   字数 min=50    max=4426
amount=99  ->   4 个 chunk   字数 min=3264  max=6015
```

**同一套参数下块从 6 字到 6015 字都有。** 4426 个汉字约 5000+ token, 超出 512-token 模型的上限。

**适用**: 边界质量要求高、且能接受块大小波动、且有额外长度兜底的场景。

### 策略 3: 长度优先 + 语义微调 ★ 推荐

```text
做法    按长度贪心吃满 -> 在【边界窗口】(相当于 overlap)里挑语义断点
        切点可以在窗口内自由移动, 而不是硬切在长度上限
```

```text
固定切块 max=800, 边界窗口=200:

块1: [0 ─────────── 800]
块2:              [600 ─────────── 1400]
                    ↑
              切点可以在这个范围里挪
```

**实测 sweep(max_chars=800):**

```text
窗口   块数   字数 min/均值/max        切点均值距离   相对全局
─────────────────────────────────────────────────────────────
   0     21     438 /   815 /  2138      0.3628        1.00x   ← 纯固定
 100     22     214 /   778 /  2138      0.4319        1.20x
 200     23     357 /   744 /  2138      0.4495        1.24x
 300     23     357 /   744 /  2138      0.4624        1.28x
 400     24     431 /   713 /  2138      0.4881        1.35x
 600     28     171 /   612 /  2138      0.5221        1.45x
```

**三个特征:**

- **窗口越大切点质量越高, 单调递增** (1.00x → 1.45x)
- **代价同步上升** —— 块数 21→28, 最小块 438→171
- **边际收益递减** —— 0→100 提升 0.20x, 400→600 只多 0.10x 却让最小块腰斩

**推荐区间: 边界窗口 = 块大小的 1/4 ~ 1/2。** OpenAI 的 50% 重叠落在这个区间上端。

**局限**: 只能微调边界, **看不见块内部的语义跳跃**。

### 策略 4: 语义优先 + 长度约束

```text
做法    先找出所有语义断点(距离 > 阈值) -> 再用长度做上下限约束
        太长补切, 太短合并
```

**实测(274 句, max_chars=800):**

```text
块数 28   字数 min 131 / 均值 612   切点均值距离 0.4821  (1.33x)
```

**和策略 3 的对比:**

```text
            块数    min    均值    切点距离
策略 3       22     357    778    0.4796
策略 4       28     131    612    0.4821
```

**切点质量几乎一样, 但策略 4 切得更碎(多 6 个块)。** 那多出来的 6 个块, 就是策略 3 看不见的那些**块内跳跃**。

**适用**: 文档内部语义跳跃密集、且能接受块偏碎的场景。

### 策略 5: 句子窗口(检索层策略)

```text
做法    每句单独成 node
        窗口存进 metadata, 不参与嵌入
        检索命中后再用 postprocessor 把窗口拼回来
代表    LlamaIndex SentenceWindowNodeParser
```

**这不是"分块策略", 是"检索粒度策略"** —— 它把"用于匹配的文本"和"送给 LLM 的文本"分开。

**实测(12 句语料, 3 个查询):**

```text
查询                              单句嵌入   窗口嵌入
────────────────────────────────────────────────
Keepalived 用什么协议同步虚拟 IP     命中 S3    偏到 S4
HAProxy 支持哪些调度算法            命中 S8    偏到 S9
怎么避免虚拟 IP 冲突                命中 S11   偏到 S12
```

**3:0, 单句嵌入全部精确命中, 窗口嵌入全部偏一格。**

**适用**: 需要"匹配精确 + 上下文完整"两个要求的场景, 作为语义分块的下一层。

## 三、嵌入机制怎么选

分块阶段要算切点距离, 有三条路:

```text
配置                     输入字符数    相对基准   说明
──────────────────────────────────────────────────────────
A. 单句嵌入                 17123      1.00x    每句一个向量
B. 窗口嵌入(radius=1)       49760      2.91x    每位置嵌 3 句
C. 单句 + metadata 前缀      36709      2.14x    前缀平均 69.5 字/句
D. 窗口 + metadata          69346      4.05x
```

### 3.1 单句 vs 窗口: 成本差 3 倍, 而且窗口有位置错位

**窗口嵌入的距离存在结构性错位:**

```text
窗口 i   = [S(i-1), S(i),   S(i+1)]
窗口 i+1 = [         S(i),   S(i+1), S(i+2)]
                    ↑ 中间两句完全相同

两个窗口的差异 = 窗口 i 独有的 S(i-1)  vs  窗口 i+1 独有的 S(i+2)
```

**`d(窗口 i, 窗口 i+1)` 测的不是"S(i) 和 S(i+1) 的差异", 而是"S(i-1) 和 S(i+2) 的差异"—— 错开两格。**

**实测验证**(用 Markdown 标题边界做弱标注, 52 个断点):

```text
机制         断点均值   非断点均值    差距      AUC
──────────────────────────────────────────────────────
单句嵌入     0.3905     0.3543      +0.0362   0.5934
窗口嵌入     0.0780     0.1010      -0.0230   0.3479    ← 比随机还差
```

**窗口嵌入不仅没帮上忙, 方向还反了。**

### 3.2 metadata 要不要进嵌入

**实测算出: 前缀比正文还长。**

```text
原文平均       62.5 字/句
metadata 平均   69.5 字/句    ← 示例格式: "file: xxx | page: N | section: xxx"
```

**成本翻倍, 而且写作方式决定一切:**

```text
写法                                      平均长度   相对基准
file: xxx.pdf | page: N | section: xxx      69.5 字     2.14x
"p12"                                        约 4 字     1.06x
不加                                         0          1.00x
```

**而且它对"找切点"没有帮助。** metadata 的价值在**检索阶段的过滤**, 不在分块阶段。

**这也印证了 OpenAI 的设计**: `attributes` 限制在 16 个 key / 256 字符, 且**只用于 `filters`, 不进嵌入**。

## 四、汇总对照表

| 策略 | 嵌入机制 | 成本 | 块大小可控 | 切点质量 | 能发现块内跳跃 | 实现复杂度 |
|---|---|---|---|---|---|---|
| 1 纯固定长度 | 不需要 | — | 高 | 1.00x(随机) | — | 极低 |
| 2 纯语义分块 | **必须窗口** | **2.91x** | **低** | 高 | — | 低(有现成库) |
| 3 长度+语义微调 | 单句 | 1.00x | 高 | 1.24~1.35x | ✗ | 中 |
| 4 语义+长度约束 | 单句 | 1.00x | 中 | 1.33x | ✓ | 中 |
| 5 句子窗口 | 单句 | 1.00x | — | 最高(检索层) | — | 中 |

**注意: "切点质量"的倍数只在单句嵌入下可比。窗口嵌入的尺度不同(见 8.4 节说明)。**

## 五、选型决策

```text
需要块大小严格可控 + 实现简单
    -> 策略 1 (纯固定长度) + 高重叠(50%)
       这是 OpenAI 的默认路线, 用重叠换边界容错

需要边界质量 + 能接受块大小波动
    -> 策略 2 (纯语义分块)
       但要外挂长度兜底, 否则会切出 4000+ 字的块

需要两者兼顾
    -> 策略 3 (长度优先 + 语义微调)      ★ 推荐起点
       边界窗口取块大小的 1/4 ~ 1/2
       成本只有纯语义分块的 1/3

块内语义跳跃密集
    -> 策略 4 (语义优先 + 长度约束)
       代价是块偏碎, 且要多调 2 个参数

需要句子级精确检索
    -> 策略 5 (句子窗口) 叠加在上面任一策略之上
       作为"第二层", 不替代分块策略
```

### 一张决策图

```text
能不能接受块大小波动?
├─ 不能 ─┬─ 要边界质量吗?
│        ├─ 要   -> 策略 3 (长度优先+语义微调)  ★
│        └─ 不要 -> 策略 1 (纯固定长度 + 高重叠)
│
└─ 能 ───┬─ 语义跳跃密集吗?
         ├─ 是  -> 策略 4 (语义优先+长度约束)
         └─ 否  -> 策略 2 (纯语义分块) + 长度兜底

无论选哪个, 如果还需要句子级精度 -> 叠加策略 5
```

## 六、可落地的工程建议

```text
1. 分块阶段用【单句嵌入】, 不用窗口嵌入
   成本 1/3, 且没有位置错位问题

2. 边界窗口取块大小的 1/4 ~ 1/2
   实测这个区间切点质量提升明显(1.24~1.35x), 块大小还稳

3. metadata 不要进分块阶段的嵌入
   前缀比正文还长, 成本翻倍, 对找切点零帮助
   它的价值在检索阶段的 filters

4. 块大小必须外挂兜底
   语义类策略都可能切出 4000+ 字的块, 或用 6 字的碎块
   超长 -> 递归字符分块再切; 过短 -> 合并回邻居

5. 换嵌入机制 = 换整个距离分布
   阈值参数不能跨机制复用, 调参前先确认用的是哪一种
```

## 七、还没解决的

**所有"切点质量"都是代理指标, 不代表检索效果。**

```text
代理指标     切点距离、块大小分布、嵌入成本     便宜, 随时可算
真实指标     recall@k / MRR                    需要标注评估集
```

### 2026-09-20 更新: 评估集已经有了, 而且跑了 —— 结论比预期更微妙

原先这里写"目前缺的是评估集"。现在有了:
`eval/qrels/phase0_url_draft.jsonl`（39 条 query，gold 锚在**原文文本**上而非 id）
+ `eval/run_eval.py`（5 阶段：dense / sparse / union / rrf / rerank）
+ 真实语义 embedding（`QwenVLEmbeddings`，1024 维，非零维 100%）。

#### 实测一: `chunk_tokens` 600/800/1200 对检索**无可测差异**

10 篇博客语料，各档独立重建 + 建索引 + 评估：

| metric（rerank 阶段） | 600 (137ch) | 800 (117ch) | 1200 (107ch) |
|---|---:|---:|---:|
| hit@5 | 0.941 | 0.941 | 0.971 |
| recall@20 | 0.912 | 0.941 | 0.971 |
| MRR@20 | 0.820 | 0.794 | 0.807 |
| nDCG@5 | 0.838 | 0.830 | 0.845 |

**差异全部 ≤ 0.03，而 n=34 → 0.03 恰好是 1 条 query。** 即噪声。

**但"参数没影响语料"是错的** —— 逐篇统计，7/10 篇的 chunk 数确实变了
（合计 137 → 117 → 107，约 15% 的 chunk 改变）。

> 所以准确的说法是: **这份 34 条 query 的评估集对 chunk 边界不敏感**，
> 而不是"chunk 大小不重要"。不能外推。

#### 实测二: 小 chunk **不是容量上限造成的**

Red Hat 手册（463 blocks）在 600/800/1200 三档下，`<100 token` 的 chunk
**都是 9 个** —— 提高上限并不减少小 chunk。

看这 9 个的构成，根因有两类：

```text
① 短 section（6/9）—— 内容驱动，调 cap 治不了
   2.4. 路由方法              section 全部正文只有  88 字符
   3.5. 配置 FTP              84 字符
   第 4 章 ...                79 字符
   4.3. 启动服务              144 字符
   5.6. 启动 HAPROXY          120 字符

② heading 无正文（2/9）—— 是缺陷
   "Red Hat Enterprise Linux 7"  tok=6   frags=['heading']
   "负载平衡器管理"              tok=8   frags=['heading']
   （封面标题，本身就没有正文块）

③ 其它（1/9）
   "索引"  tok=21，但该 section 全部正文有 1502 字符 —— 内容去了别处
```

> **结论: 想治小 chunk，调 `chunk_tokens` 是错的工具。**
> 短 section 要靠"合并进邻居"（代价：跨 section 混合），
> heading-only chunk 应该直接不产出。

#### 实测三: 两个处理方案的代价都量过了

10 篇博客语料，117 chunks（14.5% <100 token，section 纯度 100%）：

| 方案 | chunks | <100token | 跨 >1 section |
|---|---:|---:|---:|
| 现状 | 117 | 14.5% | **0%** |
| A 合并进同 parent 邻居 | 100 | 0% | **15%** ← 代价 |
| B 直接丢弃 | 100 | 0% | 0% |

**方案 B 不可行** —— 那 17 个小 chunk 里多数是**真实内容章节**，不只是致谢：

```text
## Excessive token consumption from tools makes agents less efficient  (44tok)
## Building blocks, workflows, and agents                              (53tok)
## Benefits of code execution with MCP                                (53tok)
### Concurrency is not CPU parallelism                                 (47tok)
### LIFO sends new work back to the slow process                       (60tok)
## Going from zero to one: a roadmap to great evals for agents         (61tok)
（只有 4 个是 Acknowledgements / Acknowledgments）
```

**方案 A 的代价是 15% 的 chunk 跨 section** —— 而 section 混合会稀释语义、
让 `section_path` 歧义、并让 Parent expansion 失效。

**两个方案都有真实代价，而检索指标对 chunk 变化不敏感 → 收益未证，暂不做。**

#### 实测四: 长文档**仍然测不了**

Red Hat 手册确实能压到参数（400→1600 让 chunk 数从 154 变到 76），
但**它没有可用的 qrels**：

- `eval/legacy/mixed_qrels.jsonl` 的 gold 是**裸 point_id**，README 已标注失效
- 实测验证失效：`rh_04` 问的是 `virtual_ipaddress 在哪里配置`，
  但 gold 指向的 chunk 讲的是**调度算法** —— 语义完全不对
- 该语料（`index_artifacts/chunks.jsonl`，354 chunks）是
  `source: llamaindex_fixed_semantic` 建的，与 qrels 标注时的切块不是同一份

→ **要在长文档上验证分片，必须先为它标注文本锚定的 qrels。**
   这是一件标注工作，不能靠"用当前检索结果反推 gold"（那是循环论证）。

### 更新后的待办

```text
[x] 建评估集: 39 条 query, gold 锚在原文文本 (eval/qrels/phase0_url_draft.jsonl)
[x] 用 recall@k / MRR 横向比较 chunk_tokens 600/800/1200 —— 无差异
[x] 量出小 chunk 的两个处理方案的代价 —— 都有代价, 收益未证
[ ] 为长文档(Red Hat PDF)标注文本锚定的 qrels —— 否则分片结论只在这 10 篇博客上成立
[ ] 换 2~3 份不同类型的语料重复验证
[ ] LLM 标注: 对每个相邻位置判"这里换话题了吗", 得到比标题干净的标签
[ ] rerank 侧验证(配额恢复后): candidate_k 提高是否让 rerank 受益
```

**关于 `candidate_k` 的一个提醒（2026-09-20）**：
实测把它从 20 提到 100，`union` 阶段 hit@5 从 0.824 升到 0.882（+0.058）。
**但 `union` 是 eval 专属的诊断阶段，生产路径走的是 `rrf_fuse` → rerank，
而 `rrf` 对 candidate_k 完全不敏感（恒 0.912）。**
→ 不要据此改 `candidate_k` 默认值。详见 `top_k_and_candidate_depth.md`。
