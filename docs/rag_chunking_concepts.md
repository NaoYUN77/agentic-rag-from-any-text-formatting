## 一、分块要解决什么问题

RAG 的第一步是把长文档切成小块, 因为:

```text
1. 嵌入模型有输入上限(512 / 8192 token 不等)
2. 一整篇文档压成一个向量, 语义必然被稀释
3. 检索时只应该把最相关的片段送进 LLM 的上下文
```

但"切在哪"直接决定检索质量。核心矛盾是:

```text
块太大  ->  多个主题混在一起, 向量被平均成"四不像", 主题稀释
块太小  ->  缺乏完整语义上下文, 召回多但信息量少
```

**分块策略的本质, 就是在"语义完整"和"粒度聚焦"之间找平衡点。**

## 二、前置工作: 从原始文档到可切分文本

分块质量的上限在**进分块器之前**就定了。喂进去的是垃圾, 后面每一步都在精心处理垃圾。

### 2.1 格式路由: 不同格式交给不同解析器

**没有任何一个解析器是全能的。** 每个工具都有擅长的格式和明显的盲区:

| 工具 | 来源 | 擅长格式 | 强项 | 弱项 |
|---|---|---|---|---|
| MinerU | 开源(上海AI实验室) | PDF, 扫描件 | 中文 PDF 版面还原、公式、表格、OCR | 非 PDF 格式不擅长 |
| MarkItDown | 开源(微软) | DOCX/PPTX/XLSX/HTML/PDF | 格式覆盖最广 | 复杂版面、扫描件弱 |
| Unstructured | 开源 | 20+ 格式 | 先分区再输出, RAG 生态好 | 版面还原不如 MinerU |
| Docling | 开源(IBM) | PDF/DOCX/PPTX | 结构理解、表格提取 | 中文一般 |
| Marker | 开源 | PDF | 速度快 | 中文一般 |
| PaddleOCR | 开源(百度) | 图片、扫描件 | 中文 OCR 最强 | 不做结构还原 |
| LlamaParse | 商业 | PDF/DOCX/PPTX | 云端质量高 | 数据出域、收费 |
| pdfplumber / PyMuPDF | 开源 | 有文字层的 PDF | 快、轻、零依赖 | 扫描件完全无效 |

**正确做法不是"挑一个最好的解析器", 而是按格式和内容特征把文档分派给最合适的那个** —— 这就是格式路由。

#### 路由的判定信号

```text
判定信号             用途
──────────────────────────────────────────────────────────
扩展名 / MIME        一级路由: .md/.txt 直通, .pdf 进 PDF 通道
PDF 有无文字层        有 -> 直接抽文本; 无 -> 必须走 OCR
是否含表格 / 公式     含 -> 需要高精度解析模式
语言                 中文 -> MinerU / PaddleOCR; 英文 -> Marker / Docling
数据敏感度           敏感 -> 只能本地解析, 排除云 API
规模                 批量离线 -> 云 API batch; 单篇实时 -> 本地优先
```

其中"**PDF 有无文字层**"是最关键的一次分流 —— 扫描件和电子版 PDF 需要完全不同的处理路径, 而这一步用 PyMuPDF 几毫秒就能判断。

#### 目标形态

```python
class ParserRouter:
    def route(self, path: Path) -> Parser:
        ext = path.suffix.lower()
        if ext in {".md", ".txt"}:
            return PlainTextParser()            # 不需要解析
        if ext in {".docx", ".pptx", ".xlsx"}:
            return MarkItDownParser()           # 格式覆盖最广
        if ext == ".pdf":
            if not has_text_layer(path):
                return MinerUParser(ocr=True)   # 扫描件 -> OCR
            if contains_tables(path):
                return DoclingParser()          # 表格提取强
            return MinerUParser()
        if ext in IMAGE_EXTS:
            return PaddleOCRParser()            # 中文 OCR
        raise UnsupportedFormat(ext)
```

**回退链**是容易被漏掉但很重要的一环: 主解析器失败或输出质量不达标时自动降级到备选。判据可以很直接 —— 比如输出的 Markdown 里表格全是占位符, 就该换一个解析器重试。

#### 不变的一点

无论路由到哪个解析器, **产出必须统一成带结构的 Markdown**。标题层级是后续环节最有价值的"地址"信息 —— 既能用于结构分块, 也能作为元数据挂到 chunk 上。路由换的是工具, 不换这个契约。

### 2.2 PDF -> Markdown 的完整链路

以一份 20 页的中文技术手册为例:

```text
PDF  (665 KB / 51 页, 实际取前 20 页)
 |  解析 (MinerU)
 v
Markdown      18483 字 / 520 行 / 60 个标题
 |  规则清洗
 v
干净文本      17365 字 / 492 行 / 60 个标题
 |  去掉标题行, 只留正文
 v
正文          15889 字 / 206 行
 |  句子切分
 v
句子列表      274 句
```

每一步字符量都在缩小, 但**标题层级始终保留** —— 这是有意为之, 标题是后续检索最有价值的"地址"。

### 2.3 清洗: 删掉什么

从 PDF 解析出来的 Markdown 带大量模板噪声:

| 噪声类型 | 样子 | 实测命中 |
|---|---|---|
| 目录点线 | `........第 1 章 LOAD BALANCER 概述....` | 8 行 |
| 图片占位符 | `<!-- image-->` | 12 行 |
| 目次条目 | `1.1. KEEPALIVED ...... 5` | 0 行 |
| 孤立页码 | 单独成行的数字 | 0 行 |

这类噪声的共同特征是**信息密度极低但会稀释 embedding** —— 一个 chunk 里混进半行点线, 向量就被拉偏。

### 2.4 规则清洗抓不到的噪声

**这才是真实工程的常态。** 规则只能处理可预期的噪声:

| 噪声类型 | 实例 | 实测 |
|---|---|---|
| OCR 字符混淆 | `端口8O` (应为 `80`) | 3 处 |
| 表格整体丢失 | 低精度模式输出 0 行 Markdown 表格 | 全部 |
| 公式整体丢失 | 0 行 LaTeX | 全部 |
| 页眉页脚残留 | 页码和书名混入正文 | 存在 |

对策:

```text
OCR 混淆      ->  换高精度解析模式, 或提高解析分辨率
表格/公式     ->  必须用保留结构的解析模式
页眉页脚      ->  按"每页重复出现的行"识别, 而不是靠正则硬匹配
```

**表格和公式的丢失值得特别警惕**: 一旦被压成占位符, 这部分内容对检索**完全不可见**。财务报表、参数对照表这类语料必须用能还原表格的解析器。

### 2.5 句子切分: 中文的通用问题

**这一步是跨框架的坑, LangChain 和 LlamaIndex 都栽过。**

大多数分块库的默认句子切分器是为**英文**设计的:

```text
LangChain  默认正则 (?<=[.?!])\s+         只认英文标点 + 空格
LlamaIndex 默认 NLTK punkt 分词器          基于英文语料训练
```

中文句子以 `。` 结尾且后面通常**没有空格**, 于是:

```text
同一段中文, 用默认切分器
  LangChain   ->  整篇被当成 1 句
  LlamaIndex  ->  整篇被当成 1 个 node
```

后果是距离序列算不出来, 分块直接退化。

#### 更隐蔽的第二层坑

即使改成只认中文标点, 还有一层: **不能要求标点后必须跟空白**。

```text
PDF 抽出来的文本经常是:
    "路由器上运行。所有运行 keepalived..."
                ↑ 句号后直接跟汉字
```

如果正则写成 `(?<=[。！？；])\s+`, 这类位置全部漏切。实测同一份文本:

```text
r"(?<=[。！？；])\s+"        ->  132 句   (漏切近一半)
r"(?<=[。！？；])\s*(?=\S)"  ->  274 句   (正确)
```

#### 一个可复用的中文切分正则

```python
r"(?<=[。！？；])\s*(?=\S)"
```

三个部分各自解决一个问题:

```text
(?<=[。！？；])   切在句末标点之后; 逗号不参与(避免切出半句话)
\s*              顺带吃掉紧随的空白, 换行也算
(?=\S)           要求后面还有非空白内容, 避免文本以句号结尾时切出空片段
```

**最后的 `(?=\S)` 是个变通**。如果框架允许传一个切分函数(而不是正则字符串), 直接在函数里过滤空串更干净:

```python
def zh_splitter(text: str) -> list[str]:
    return [s.strip() for s in re.split(r"(?<=[。！？；])", text) if s.strip()]
```

## 三、语义分块的五步流程

传统分块按**长度**切: 到 512 token 就下刀, 不管切在哪。语义分块换了个判据: **不看长度, 看语义跳变**。

```text
递归字符分块:  切在"长度超了"的地方
语义分块:      切在"意思变了"的地方
```

### 第 1 步: 句子分割

按句末标点把文本切成一串句子。只有这一刀, 没有层级、没有降级。

**逗号不参与切分。** 逗号是句内停顿, 在逗号处切只会得到半句话:

```text
"分片粒度直接决定检索质量，块太大会稀释语义。"
  按句号切 -> 1 句  (正确)
  按逗号切 -> "分片粒度直接决定检索质量，"  +  "块太大会稀释语义。"  (语义残缺)
```

切完之后, 每句话就是后面计算的最小单元, 也决定了最终块的粒度下限 —— **一个块最少包含一句话**。

### 第 2 步: 上下文感知嵌入

给每个句子配一个**滑动窗口**: 以它为中心, 前后各取 N 句, 拼成一段文字, 再送进嵌入模型。

```text
句子:  S1  S2  S3  S4  S5  S6

给 S3 配窗口: [S2  S3  S4]
给 S4 配窗口:     [S3  S4  S5]     <- 窗口右移一格
```

窗口宽度 = `2 × N + 1`。首尾句子的窗口会自动变窄。

**为什么需要它**: 单句嵌入会制造假信号。`"然后执行第三步"` 单独看语义残缺, 距离会反常地大, 算法误以为换了话题。带上前后文之后语义完整, 距离才正常。

**关键理解**: 上下文不是模型的能力, 是调用方喂进去的。模型收到的就是一段已经拼好的普通文本, 它不知道哪句是中心句。

**边界处理**: 构造窗口时必须夹紧左右边界。注意有些语言用负数下标取"倒数第几个元素"(Python 就是如此), 不夹紧的话第一句会把**最后一句**当成前文拼进去 —— 程序不报错, 但向量被彻底污染。

### 第 3 步: 计算相邻距离

每个窗口算一个向量, 然后比较**相邻两两**:

```text
similarity = cosine_similarity(vec_i, vec_i+1)
distance   = 1 - similarity
```

n 个句子产出 **n-1** 个距离值。

**距离指的是余弦距离**, 衡量两个向量的**方向夹角**, 与向量长度无关:

```text
距离 = 0      方向完全一致, 语义几乎相同
距离 ≈ 1      方向正交, 语义无关
距离 = 2      方向完全相反
```

不用欧氏距离的原因: 两段内容相同但长度不同的文字, 欧氏距离会因为长度差判为不相似, 余弦只看方向。

### 第 4 步: 识别断点

距离值本身不告诉你要不要切, 还要判断**哪些算"异常高"**。

**不能用固定阈值** —— 真实模型的距离普遍很小很集中, 设一个绝对值可能一刀都切不出来。必须用**相对判断**。

### 第 5 步: 合并成块

断点**之间**的句子合并成一个 chunk。断点下标 `i` 表示"第 i 句和第 i+1 句之间那条缝", 第 i 句归前一块。

```text
for index in 断点下标:
    本块 = sentences[start : index + 1]     # 含第 index 句
    输出本块
    start = index + 1
最后一块 = sentences[start:]
```

**切口永远落在两句话之间**, 不会切开一句话。

**语义分块的输出是没有重叠的** —— 每句话只属于一个块。这和递归字符分块默认带的 `chunk_overlap` 完全不同。

**"合并成块"的准确说法是"相邻且中间没有检测到断点的句子合并成一块"**, 而不是"语义相近的句子合并"。这两者听起来差不多, 但含义不同:

> 算法判断的是"这两句之间有没有越过阈值", 不是"这两句语义是否真的相近"。一段连续的话题如果整体平缓、没有尖峰, 会被整块合并 —— 哪怕它内部其实换了三个小话题。

这就是最终产物可能**超出嵌入模型输入上限**的原因。

## 四、余弦相似度 vs 余弦距离

**这是最容易搞混的一处: 同一个"余弦", 在两个阶段的方向正好相反。**

```text
分块阶段   算【余弦距离】     距离越大 = 差异越大   = 越可能是分块边界
检索阶段   算【余弦相似度】   相似度越大 = 越像     = 越该排在前面
```

两个量互为反义词:

```text
余弦相似度 = 两个向量夹角的余弦值    范围 [-1, 1]    越大越相似
余弦距离   = 1 - 余弦相似度          范围 [0, 2]     越小越相似

关系:  相似度 + 距离 = 1
```

### 4.1 对照表

| 语义关系 | 夹角 | 余弦相似度 | 余弦距离 |
|---|---|---|---|
| 方向完全一致 | 0° | **1.0** | **0.0** |
| 很接近 | 小 | 0.9 | 0.1 |
| 有点相关 | 中 | 0.5 | 0.5 |
| 正交(无关) | 90° | 0.0 | 1.0 |
| 方向完全相反 | 180° | **-1.0** | **2.0** |

**每一行里 相似度 + 距离 = 1。** 它们看的是同一个夹角, 只是从两头描述:

```text
问"这两句像不像?"  ->  看相似度, 越高越像
问"这两句差多少?"  ->  看距离,   越小越像
```

### 4.2 为什么两个阶段要用不同的量

因为**要找的东西不同**:

```text
要找"最像的"     ->  用相似度, 从大到小排序, 取 top-K       (检索)
要找"差异最大的"  ->  用距离,   从小到大排序, 取最大的那些   (找边界)
```

本质上是一回事 —— 都是看夹角。只是一个问"像不像", 一个问"差多少"。

### 4.3 实际数字长什么样

**分块阶段(距离)**:

```text
d(0,1) = 0.0342   <- 距离很小 = 这两句很像
d(4,5) = 0.1700   <- 距离最大 = 这两句差得最多 = 可能是边界
阈值   = 0.1690   <- 超过它就是边界
```

**检索阶段(相似度)**:

```text
第 1 名  0.7885   <- 相似度最高 = 最相关
第 2 名  0.7506
分差     0.0379   <- 第一名领先多少, 反映"检索有多确定"
```

### 4.4 判断一个 score 是相似度还是距离

**不同向量库返回的东西可能完全相反:**

```text
LlamaIndex SimpleVectorStore    返回【相似度】  越大越好
FAISS                           默认返回【距离】 越小越好
Chroma                          默认返回距离, 可配置
Pinecone                        取决于 metric 配置
```

判断方法: 看排序结果。

```text
top-1 的 score 是最大值   ->  相似度
top-1 的 score 是最小值   ->  距离
```

数值范围也能提示:

```text
分数都在 0~1 且偏高          ->  多半是余弦相似度
分数是 0 / 0.3 / 1.2 这种    ->  多半是欧氏距离
分数带负数                   ->  一定是相似度
                                (距离不可能为负)
```

**换向量库时这个语义可能整个反转, 必须确认。**

### 4.5 一个实测佐证

用三个向量方向已知的文档做检索(嵌入函数固定返回指定向量):

```text
手算余弦:
  文档A vs 查询 =  1.0   完全相同方向
  文档B vs 查询 =  0.0   正交
  文档C vs 查询 = -1.0   完全相反

LlamaIndex retrieve() 返回:
  1.0000   文档A_与查询完全相同     <- 排第一
  0.0000   文档B_与查询正交         <- 排第二
  -1.0000  文档C_与查询相反         <- 排第三
```

**排序从大到小, 且出现负数 —— 确认返回的是相似度, 不是距离。**

## 五、断点判定的四种统计方法

四种方法的公式(与框架无关):

```text
percentile          取距离序列的第 P 百分位
standard_deviation  均值 + k × 标准差
interquartile       均值 + k × IQR     (IQR = Q3 - Q1)
gradient            先算距离的变化率, 再取百分位
```

默认参数通常为 `P=95`、`k=3`、`k=1.5`、`P=95`。

### 各自的实测表现

在 10 句语料上:

```text
percentile            阈值 0.1690   ->  2 块   切在对的位置
standard_deviation    阈值 0.2320   ->  1 块   一刀没切
interquartile         阈值 0.1678   ->  2 块   切在对的位置
gradient              阈值 0.0969   ->  2 块   切在假断点上
```

在 274 句语料上, 差异才真正拉开:

```text
percentile            ->  15 块
standard_deviation    ->   5 块
interquartile         ->  11 块
gradient              ->  15 块
```

### 逐方法说明

**percentile 百分位法** —— 最合理的默认值

把距离从小到大排列, 取第 P 百分位当门槛。优势是**自适应**: 不管距离集中在什么量级, 都自动缩放到合适位置。换模型、换语料都不用改参数。

缺点是**样本少时会失效**。9 个距离值时, 95 百分位几乎等于最大值, **最多只能切 1 刀**。这不是 bug, 是数学必然:

```text
9 个点, 95 百分位 ≈ 第 8.55 个点的值 ≈ 最大值
比它小的点全都够不着 -> 只有 1 个越线
```

**standard_deviation 标准差法** —— 容易失效

思路来自统计学的 3σ 原则。问题是它**假设距离服从正态分布, 而这个假设不成立** —— 距离序列通常是右偏的、有界的, 样本量还很小。

更要命的是**它对极端值敏感**: 标准差是平方和开方, 一个特别大的距离会把 std 拉高, 导致阈值升高, **反而更难切出断点**, 和直觉相反。

实测就是最好的例子: 语义上最明显的那道分界被它直接忽略了, 整篇挤成一个块。

**interquartile 四分位距法** —— 比标准差法稳健

IQR 是 Q3 减 Q1, 只看数据的排序位置, 不受极端值数值大小的影响。你把最大的距离从 0.17 改成 1.7, Q1 和 Q3 几乎不变。

注意有些实现用的是 `均值 + k×IQR`, 而标准箱线图规则是 `Q3 + k×IQR`。两者在有偏分布上会有差异, 对照不同框架时要注意。

**gradient 梯度法** —— 最反直觉

它**不看距离本身的大小, 看距离的变化率**。想解决的是"语义渐变、没有尖峰"的文档(法律条文、医学指南)。

但**这里有个陷阱**: 梯度模式返回的是**梯度数组**, 而切点下标是从这个数组取的。所以位置可能落在"变化最剧烈"的地方, 而不是"距离最大"的地方。

实测中它被"低点反弹"骗了:

```text
d(0,1) = 0.0342   <- 全篇最小值
d(1,2) = 0.1676   <- 突然跳到近 5 倍

从 0.0342 跳到 0.1676 是全篇"上升最快"的落差
-> 梯度最大 -> 被判为断点
```

结果切在第一句和第二句之间, 而这两句明明在讲同一个话题 —— 典型的假断点。

### 汇总

| 方法 | 稳健性 | 主要问题 | 建议 |
|---|---|---|---|
| `percentile` | 高 | 样本少时最多切 1 刀 | **默认选择** |
| `standard_deviation` | 低 | 3σ 过高; 极端值反噬 | 谨慎 |
| `interquartile` | 中高 | 与标准箱线图规则可能不一致 | 分布有偏时可用 |
| `gradient` | 中 | 下标语义变了, 易切假断点 | 只在渐变型文档上试 |

**只需要调两个参数**:

```text
1. 阈值松紧(amount)   先固定窗口半径, 用它控制切几块
2. 窗口半径(N)        块数合适之后, 再调它微调边界位置
```

判定方法本身用默认的 percentile 就够了 —— 实测它和 interquartile 常给出相同结果, 而另外两个一个容易失效、一个容易切错。

## 六、窗口的两种角色

这是最容易混淆的一点。**"窗口"这个词在两个不同的设计里指两件相反的事:**

```text
角色 A: 窗口是【嵌入的输入】
        把窗口拼成一段文字 -> 嵌入 -> 用向量距离决定切在哪
        代表: LangChain SemanticChunker / LlamaIndex SemanticSplitterNodeParser

角色 B: 窗口是【检索的输出】
        只嵌单句 -> 检索命中 -> 再把窗口拼回来送给 LLM
        代表: LlamaIndex SentenceWindowNodeParser
```

| | 角色 A(找边界) | 角色 B(补上下文) |
|---|---|---|
| 切分依据 | 语义距离 | 句号 |
| 窗口参与嵌入吗 | **参与** | **不参与** |
| 嵌入的对象 | 窗口(多句拼一起) | 单句 |
| 窗口的用途 | 决定"在哪切" | 检索后"补上下文" |
| 需要嵌入模型吗 | 必须 | 不需要 |

**它们解决的是两种不同的失败:**

```text
失败 A: 切点切错了
        一句话被从中间劈开, 两块都不完整
        -> 角色 A 解决(找更好的边界)

失败 B: 块本身缺背景
        "该公司营收增长 3%" —— 哪家公司? 哪个季度?
        -> 角色 B 解决(检索后补上下文)
```

**各自的弱点:**

- 角色 B 的前提是"句子本身要自足"。文档里如果大量出现 `"然后执行第三步"`、`"该参数默认关闭"` 这类指代和省略, 单句嵌入会因为语义残缺而失效 —— 这时候角色 A 反而有优势。
- 角色 A 的窗口向量是多个句子的混合体, 匹配时指向不够精确。实测同一份语料、同样 4 个查询, 角色 B 的 top-1 命中率是 4:0。

**两者可以叠加:**

```text
第一层  语义分块        ->  把长文档切成话题块          (解决失败 A)
第二层  句子窗口索引     ->  句子级精确检索 + 窗口补全   (解决失败 B)
```

## 七、关键工程结论

### 7.1 块大小完全失控

以 274 句语料为例, **同一套参数下**:

```text
阈值松                 ->  137 个块, 最小 6 字, 最大 2901 字
阈值紧(默认)           ->   15 个块, 最小 50 字, 最大 4426 字
阈值最紧               ->    4 个块, 最小 3264 字, 最大 6015 字
```

**块从 6 字到 6015 字都有。** 4426 个汉字约 5000+ token, 已经超出 512-token 模型的上限。

**语义分块只保证"边界合理", 不保证"大小合理"。** 生产上必须在外面再套一层长度约束: 超长块用递归字符分块再切, 过短块合并回邻居。

### 7.2 距离尺度随窗口半径整体缩放

实测同一份语料、不同窗口半径:

```text
窗口半径   窗口宽度   距离范围          阈值
──────────────────────────────────────────────
    0       1 句     0.2248 ~ 0.4747   0.4692
    1       3 句     0.0342 ~ 0.1700   0.1690
    2       5 句     0.0099 ~ 0.1372   0.1324
    3       7 句     0.0099 ~ 0.0914   0.0850
```

**距离尺度差了约 5 倍。** 原因在窗口重叠率:

```text
窗口半径 0   相邻窗口共享 0 句     距离大
窗口半径 1   相邻窗口共享 2/3      距离中
窗口半径 2   相邻窗口共享 4/5      距离小
窗口半径 3   相邻窗口共享 6/7      距离极小
```

窗口越宽, 相邻两个向量越像, 剩下那点差异被平均掉。

**结论: 阈值参数不能跨窗口半径复用。** 换了窗口半径, 等于换了整个距离分布, 参数必须重新调。

### 7.3 样本量决定统计方法有没有区分度

```text
9   个距离值   percentile 和 interquartile 结果完全相同
273 个距离值   两者分化成 15 块 vs 11 块
```

**样本量小的时候, 四种方法看起来都一样** —— 这时候选哪个都行, 但也说明结果不可信。要判断某种方法是否合适, 得在真实规模的语料上跑。

### 7.4 嵌入函数必须真懂语义

用不具语义能力的嵌入函数跑这套流程, 效果会退化成"基于词面重叠的比较"。判断方法很简单 —— 跑一组对照:

```text
语义相近的对照                       真模型    纯哈希
────────────────────────────────────────────────────
汽车 / automobile        跨语言同义   0.782    0.000
如何部署系统 / 安装步骤如下  同义改写    0.642    0.000
退货流程 / 退换货怎么走     同义改写    0.853    0.000
如何部署系统 / 今天天气不错  不相关     0.359    0.000
```

真模型给"汽车 / automobile"打 0.782(一个字都不重叠), 哈希给 0.000。**哈希函数不是"不太精确", 是完全没有语义。**

注意最后一行: 不相关的对照也拿到 0.359。**真实嵌入的相似度普遍偏高, 这正是不能用绝对阈值的原因。**

### 7.5 嵌入在 RAG 里出现三次

```text
1. 分块时的窗口向量     找断点      用完即弃
2. 入库时的 chunk 向量   供检索      持久化
3. 查询时的 query 向量   做比对      每次提问都算
```

第 1 步和第 2 步会重复嵌入大量重叠的文本, 生产上值得做缓存复用。

另外注意分工: **嵌入服务(百炼/OpenAI)只做"文本 -> 向量", 距离计算全在本地的 numpy / scikit-learn 里**。只有向量数据库做相似度检索时才在服务端算距离。

## 八、分块策略全景

### 8.1 策略清单(按使用频率)

```text
递归字符分块 + overlap       最普遍, 便宜、可控、够用
结构分块(按标题/章节)         结构化文档的首选
固定长度分块                  最简单, 但切点不讲究   ← OpenAI 的默认
句子级索引(窗口补上下文)      高精度检索场景
语义分块                      补充或实验手段, 不是默认
长度 + 语义混合               生产推荐的折中方案      ← 8.3
```

### 8.2 语义分块的代价

| 代价 | 表现 |
|---|---|
| 钱和时间 | 每句话都要嵌一次。100 万字文档 = 几十万次嵌入调用 |
| 块大小不可控 | 主题长就切出大块, 可能超出模型输入上限 |
| 结果不可预测 | 调一下窗口半径或阈值, 切分结果就变 |
| 调参成本高 | 没有通用最优参数, 每个语料都要重新试 |

**常见做法是先用结构或长度粗切, 只在边界模糊的地方做语义判断**, 而不是全文逐句嵌入。

### 8.3 长度 + 语义的两种混合路线

纯长度切点随语义随机, 纯语义切块大小失控。折中方案有两条路线, 方向相反:

```text
路线 ①  长度优先 + 语义微调
        按长度贪心吃满 -> 在【块尾的边界窗口】里挑语义断点
        - 块大小天然受控
        - 只能微调边界, 看不见块【内部】的语义跳跃

路线 ②  语义优先 + 长度约束
        先找出所有语义断点(距离 > 阈值) -> 再用长度做上下限约束
        - 能发现任意位置的跳跃
        - 需要多调 2 个参数(阈值 + 最小块), 否则块会偏小
```

**路线 ① 的"边界窗口"就是常说的 overlap**:

```text
固定切块 max=800, overlap=400:

块1: [0 ─────────── 800]
块2:            [400 ─────────── 1200]
                  ↑ overlap 区 = 切点可以移动的范围

在 [400, 800] 里找语义距离最大的位置下刀, 而不是硬切在 800
```

#### 实测对比(274 句语料, max_chars=800)

> **前提: 这组数据用的是【单句嵌入】** —— 每句话各自嵌一个向量, 再算相邻句子的余弦距离。
> **不是上下文嵌入(窗口), 也没有用到 metadata 机制。**
>
> ```python
> vecs  = emb.embed_documents(sents)                      # 单句, 不拼窗口
> dists = [1 - cos(vecs[i], vecs[i+1]) for i in ...]      # 相邻单句比距离
> ```
>
> 换一种嵌入机制, 距离尺度会变, 这组数字就不可比 —— 见 8.4 末尾的说明。

**全局相邻距离均值 0.3612** —— 这是"随机切点"的期望值, 作为基准线。

```text
策略                        块数   字数 min/均值    切点均值距离   相对基准
──────────────────────────────────────────────────────────────────────
A. 纯固定长度                21   438 / 815       0.3628        1.00x
C. 长度优先 + 语义微调        22   357 / 778       0.4796        1.33x
D. 语义优先 + 长度约束        28   131 / 612       0.4821        1.33x
```

**三个可读的结论:**

- **A 的切点距离 0.3628 几乎等于全局均值 0.3612** —— 这不是巧合, 随机位置的平均距离期望就是全局均值。**说明纯固定长度的切点没有任何语义偏好。**
- **C 和 D 都明显高于基准(1.33x)** —— 语义微调确实把切点挪到了语义跳变处。
- **D 块数更多(28 vs 22)、块更小** —— 它能看到 C 看不见的块内跳跃, 代价是块偏碎。

> 数据来源: `pipeline/experiments/04_chunking_strategies.txt`

### 8.4 边界窗口开多大

窗口越大, 切点能移动的范围越远, 找到真断点的机会越大 —— 但块数也会增加、块大小开始不稳。

**实测 sweep(max_chars=800):**

```text
窗口   块数   字数 min/均值/max        切点均值距离   相对基准
─────────────────────────────────────────────────────────────
   0     21     438 /   815 /  2138      0.3628        1.00x
 100     22     214 /   778 /  2138      0.4319        1.20x
 200     23     357 /   744 /  2138      0.4495        1.24x
 300     23     357 /   744 /  2138      0.4624        1.28x
 400     24     431 /   713 /  2138      0.4881        1.35x
 600     28     171 /   612 /  2138      0.5221        1.45x
```

**趋势很干净: 窗口越大, 切点质量单调提升。**

**但代价也单调上升:**

```text
块数        21 -> 28        (+33%)
最小块      438 -> 171      (块大小开始不稳)
```

**边际收益递减**: 0→100 提升了 0.20x, 而 400→600 只多 0.10x, 却让最小块从 431 掉到 171。

**推荐区间: 窗口 = 块大小的 1/4 ~ 1/2。**

```text
OpenAI 的默认值(800 token 块 + 400 token 重叠 = 50%) 落在这个区间的上端
本实测里 50% 对应的切点质量是 1.35x, 块大小还稳
```

> 数据来源: `pipeline/experiments/05_window_sweep.txt`

#### 一个必须注意的前提: 距离尺度取决于嵌入机制

上面所有"相对基准"的倍数, 都以**单句嵌入**的全局均值 0.3612 为分母。**换一种嵌入机制, 这个分母就变了:**

```text
窗口嵌入(前后各 1 句)     距离范围 0.0342 ~ 0.1700     阈值 0.1690
单句嵌入                 距离范围 0.3600 ~ 0.5200     全局均值 0.3612
```

**同一份语料、同一个模型, 只因为"嵌窗口"还是"嵌单句", 距离尺度差了一倍。**

原因是窗口嵌入让相邻向量更相似(相邻窗口共享 2/3 内容), 距离被整体压小。

**实践含义**: 用哪种机制做切点判定就一直用同一种, **不要把两个实验的阈值混用**。调参时也要注意, 换机制等于换了整个距离分布。

### 8.5 成本: 主要差在"嵌窗口"还是"嵌单句"

同样 274 句语料, 三种做法的嵌入输入量:

```text
方案                            嵌入对象           输入量     相对基准
──────────────────────────────────────────────────────────────────
纯语义分块(buffer_size=1)        274 个三句窗口      49214 字   2.87x
全句嵌入 + 边界窗口微调           274 个单句          17123 字   1.00x
只嵌"边界窗口"内的句子            186 个单句          13016 字   0.76x
```

**两个反直觉的结论:**

**① 成本主要差在"嵌窗口"和"嵌单句", 不在"嵌全部"和"嵌边界"。**

纯语义分块要对每个位置嵌入一个三句窗口, 所以输入量是语料的近 3 倍。任何"单句嵌入"方案都在 1.0x 上下。

**② "只嵌边界窗口"省得比想象中少。**

因为窗口大小和块大小是联动的:

```text
块上限   边界数   需嵌句子数   占全部   输入量
  400     42        271        99%     1.00x   ← 完全没省
  800     20        186        68%     0.76x
 1600     10         96        35%     0.45x
 3200      5         50        18%     0.17x
```

**块越小, 边界窗口覆盖的句子越多** —— 400 字的块基本等于全嵌。而常用的块大小恰好在这个区间。

**还有一个矛盾**: 块越大越省, 但块越大检索精度越差。**省钱的方案和好用的方案是反向的。**

> 数据来源: `pipeline/experiments/05_window_sweep.txt` 与本节的推导计算

#### 还有一种成本容易被忽略: metadata 拼进嵌入

如果给每个 chunk 前置 metadata 再嵌入, 成本会明显上升:

```text
配置                          输入字符数    相对基准
──────────────────────────────────────────────────
A. 单句嵌入                    17123       1.00x
B. 窗口嵌入(radius=1)          49760       2.91x
C. 单句 + metadata 前缀         36709       2.14x
D. 窗口 + metadata             69346       4.05x

示例 metadata:  "file: redhat-lb.pdf | page: 12 | section: 第 2 章 KEEPALIVED"
平均长度 69.5 字/句, 而正文平均只有 62.5 字/句
```

**metadata 前缀比正文还长 —— 输入量直接翻倍。**

**写法决定成本:**

```text
file: xxx.pdf | page: N | section: xxx    69.5 字    2.14x
"p12"                                      约 4 字    1.06x
不加                                       0         1.00x
```

**这解释了为什么 OpenAI 把 `attributes` 限制在 16 个 key、每个 256 字符, 而且只用于 `filters` 不进嵌入。**

**结论: metadata 的价值在检索阶段的过滤, 不在分块阶段。** 把它拼进分块用的嵌入, 是花两倍成本换零收益。

> 数据来源: `pipeline/experiments/09_embedding_config_compare.txt`
> 详细分析见 `pipeline/experiments/findings/03_embedding_mechanism.md`

### 8.6 结构分块 + 文本切分的串联模式

先用结构切出逻辑块, 再按长度细化:

```text
Markdown 标题层级  ->  逻辑块(带标题路径元数据)
                   ->  再对每个逻辑块做长度切分
```

这样既保住了文档结构, 又控制了块大小。第二次切分出的小块**继承标题元数据**, 相当于给每块一个精确的"地址"。

### 8.7 什么时候该真去建评估集

上面所有指标(**切点处的平均语义距离**)都是**代理指标** —— 它衡量"切点是否落在语义跳变处", 但**不代表检索效果就好**。

```text
代理指标          切点距离、块大小分布、嵌入成本      -> 便宜, 随时可算
真实指标          recall@k / MRR / Precision@k      -> 需要标注评估集
```

**要判断"哪种分块更好", 只能靠真实指标。** 代理指标的作用是快速筛掉明显不合理的配置, 不是最终依据。

**建评估集的最低要求**:

```text
1. 一批查询(10~100 条)
2. 每条查询标注出"哪些块是相关的"
3. 或者用 LLM 从语料反向生成问答对(弱标注, 但够做相对比较)
```

> 这部分尚未在项目中实现, 所有"M 比 N 好"的结论目前都只是间接推断。

## 九、相关策略

### 9.1 Anthropic Contextual Retrieval

同样是"给 chunk 补上下文", 但做法更重:

```text
本文的窗口做法:   拼前后各 N 句原文           -> 嵌入
Contextual:      LLM 生成 chunk 级背景摘要    -> 前置到 chunk -> 嵌入
```

用 LLM 为**每个 chunk** 生成 50-100 token 的说明性上下文, 用的是这样的 prompt:

```text
<document>
{{WHOLE_DOCUMENT}}
</document>
Here is the chunk we want to situate within the whole document
<chunk>
{{CHUNK_CONTENT}}
</chunk>
Please give a short succinct context to situate this chunk within the
overall document for the purposes of improving search retrieval of the
chunk. Answer only with the succinct context and nothing else.
```

效果(以 1 - recall@20 为指标, 越低越好):

```text
基线                     5.7%
+ Contextual Embeddings  3.7%   失败率降 35%
+ Contextual BM25        2.9%   失败率降 49%
+ Reranking              1.9%   失败率降 67%
```

**两个子技术**: Contextual Embeddings(前置上下文再嵌入) + Contextual BM25(同一份前置文本也建 BM25 索引)。两者叠加比单独用任何一个都好。

**成本**: 借助 prompt caching, 生成这些上下文的一次性成本约 $1.02 per million document tokens —— 只在建库时付一次。

**它明确否定了两种更简单的做法**: 给 chunk 加通用文档摘要(收益极其有限)、以及 summary-based indexing(实测性能低)。区别在于它生成的是 **chunk-specific** 的上下文, 不是泛泛的文档摘要。

**官方给的四条实现建议**:

```text
1. chunk 边界   大小、切点、重叠都会影响检索效果
2. 嵌入模型     对所有模型都有提升, 但有些模型受益更明显
3. 自定义 prompt 可以针对领域调整(比如附上术语表)
4. top-K 数量   试了 5/10/20, 20 最好
```

**一个前提判断**: 如果知识库小于 20 万 token(约 500 页), 直接把全部内容塞进 prompt 就行, 不需要 RAG。

### 9.2 层级分块 + 自动合并

另一种补上下文的思路, 是**纵向扩展**而不是横向:

```text
一次切成多个层级:  chunk_sizes = [2048, 512, 128]
每个小节点持有父节点引用

检索时命中的是小块(精确)
当命中的子块数量超过阈值, 自动向上替换成父块(完整)
```

这解决的是"检索粒度"和"上下文粒度"的矛盾。和窗口法的区别:

```text
窗口法    横向扩: 命中小句 -> 左右各取 N 句
层级法    纵向扩: 命中多个小片 -> 合并成父块
```

## 十、框架对照

同一个概念在不同框架里的名字:

| 概念 | LangChain | LlamaIndex |
|---|---|---|
| 分块抽象 | `TextSplitter` | `NodeParser` |
| 输出对象 | `Document` | `Node` |
| 批量切分 | `split_documents()` | `get_nodes_from_documents()` |
| 语义分块 | `SemanticChunker` | `SemanticSplitterNodeParser` |
| 句子窗口 | 无原生实现 | `SentenceWindowNodeParser` |
| 层级分块 | 无原生实现 | `HierarchicalNodeParser` |
| 窗口替换 | 需自己实现 | `MetadataReplacementPostProcessor` |
| 窗口半径 | `buffer_size` | `window_size` / `buffer_size` |
| 断点阈值 | `breakpoint_threshold_amount` | `breakpoint_percentile_threshold` |

**关键差异: metadata 是否参与嵌入**

```text
LangChain Document   metadata 默认不参与嵌入(只嵌 page_content)
LlamaIndex Node     metadata 默认会拼进嵌入文本,
                    需要用 excluded_embed_metadata_keys 显式排除
```

这一点直接决定了"单句嵌入 + 窗口元数据"这种模式能不能原生实现。

具体细节见两个专栏文档。
