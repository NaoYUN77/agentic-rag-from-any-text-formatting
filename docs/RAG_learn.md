## 一、主线文章评价

《RAG 全链路原理剖析》(约 10 万字, 公众号"徐同学呀") 是一篇值得精读的**全景手册**, 但更适合作为"第二遍读"的材料: 先动手跑通一个最小 RAG, 再回头翻它, 每章都能对上号。

**优点**

- 管线完整: 清洗 -> 分片 -> 向量化 -> 索引 -> 查询改写 -> 混合召回 -> 重排 -> 生成 -> 评估 -> 调优, 十章对应一条真实工程链路
- 原理讲到根上: BM25 公式逐项拆解、池化为什么有损、ColBERT 延迟交互、Bi-encoder vs Cross-encoder, MRR/MAP 附手算示例
- 工程视角足: 解析工具对比表、嵌入模型选型表、按 ROI 排序的调优优先级

**短板**

- 全程无可运行代码, 知道"为什么"但看不到"怎么跑"
- 10 万字篇幅大, 不适合一口气读完; 个别章节编号跳号、有笔误
- 部分关键内容藏在插图中

**建议章节顺序**: 第 1-3 章 (清洗/分片/向量化) -> 第 5-8 章 (检索与生成) -> 第 9-10 章 (评估与调优), 第 4 章索引细节可后置。

## 二、核心概念速查

| 概念 | 一句话解释 |
|---|---|
| RAG | 检索增强生成: 先从外部知识库检索相关片段 (top-K), 再让 LLM 基于片段作答, 即"开卷考试" |
| 语料 (corpus) | 喂给系统的原始文本素材集合, 与格式无关; 边界是"能解析成有语义的文本" |
| 嵌入向量 (embedding) | 用模型把文本压缩成固定长度的数字数组 (如 768/1024/1536 维), 语义相近则向量相近 |
| 维度 | 向量里数字的个数, 由模型架构决定; 不同模型的向量互不可比 |
| 稠密向量 | 每维都有值, 编码语义, 能跨词匹配 ("汽车"~"automobile") |
| 稀疏向量 | 维度=词表大小, 只有出现过的词非零, 编码字面匹配, 强于精确命中编号/术语 |
| 混合搜索 | 稠密 + 稀疏两路召回, 用 RRF 等方式融合排序, 语义召回与精确命中互补 |
| Top-K | 按相似度从高到低排序后只返回前 K 条; `n_results=5` 即 top-5; 无质量门槛, 常配合阈值过滤 |
| 分片 (chunking) | 把长文档切成语义完整的检索粒度; 常用 512 token + 80 token 重叠; 代码按语法树切 |
| 重排序 (rerank) | Cross-encoder 对召回候选逐对精排, 慢而准; Bi-encoder 快而粗, 两者配合用 |
| 语料 vs 知识库 | 语料是生料, 知识库是清洗/分片/建索引后的成品; 语料质量决定检索上限 (Garbage In, Garbage Out) |
| RAG vs LLM Wiki | RAG 存原文碎片、按需检索、可溯源; LLM Wiki 是 LLM 预先消化源材料生成的结构化页面, 全局但多一层幻觉风险; 实践中常把 wiki 页也喂进 RAG 索引 |

## 五、概念答疑精选

> 按主题归类的逐点追问整理, 每个问题都给出了直观解释和易踩的坑。

### 5.1 主流检索方法: 只有 BM25 吗

不是。BM25 只是"词汇检索"这一派的代表, 现代 RAG 的完整形态是 **两大流派 + 融合 + 精排**。

**流派一: 词汇 / 稀疏检索 (字面匹配)**

- **TF-IDF** - BM25 的前身, 词频线性增长且不校正文档长度, 已被取代
- **BM25 / BM25+** - 事实标准, Elasticsearch / Lucene / OpenSearch 的默认相似度算法
- **SPLADE** - "学习型稀疏": 维度仍是词表大小, 但权重由神经网络学出, 而非纯统计, 可理解为"神经版 BM25"
- **bge-m3 的 sparse 输出** - 同类思路, 一套模型同时产出 dense + sparse

**流派二: 稠密 / 语义检索**

- **Bi-encoder 双塔** - query 和 chunk 各自独立编码成向量算距离, 现代 RAG 的默认主力
- **ANN 索引** - HNSW / IVF / PQ 做近似最近邻, 避免 O(n) 暴力比对
- **ColBERT (延迟交互)** - 每个 token 存一个向量, 检索时算 token 级 MaxSim 求和, 精度接近 Cross-encoder 而速度远快

**融合: 混合检索 (Hybrid)**

- **RRF (倒数排名融合)** - 两路各取 top-K, 按排名倒数加权合并, 不要求分数可比
- **加权分数融合** - 归一化后按权重相加, 需要额外调权重
- 典型组合: dense (bge-m3) + sparse (BM25 或 SPLADE)

**精排: Cross-encoder Reranker**

bge-reranker-v2-m3、Cohere Rerank 等, 对候选逐对精确打分。它本身不算"检索", 但属于检索链路的一部分。

**其他范式**

- **GraphRAG** - 知识图谱做社区级检索, 擅长"总结整个语料在讲什么"这类全局问题
- **Agentic Search** - 不一次检索定胜负, 多轮改写 query 迭代搜索
- **Query 侧改造** - HyDE、MultiQuery、查询改写, 改的不是检索算法而是 query 本身

**结论**: 默认答案是 `hybrid = dense + BM25 (或 SPLADE) + rerank`, 而不是单选 BM25。BM25 是最经典、最稳定、最便宜的那一个, 但只是主力之一。

### 5.2 语料的边界在哪里

语料 (corpus) 就是**喂给系统的原始文本素材集合**, 与文件格式无关。判断标准只有一条: **能不能解析成有语义的文本**。

| 来源 | 算语料吗 | 说明 |
|---|---|---|
| PDF / Word / PPT / MD / TXT | 算 | 走对应解析器归一到文本 |
| 网页 URL | 算 | URL 只是指针, 抓取并提取出的正文才是语料 |
| 邮件 / 聊天记录 / 工单 | 算 | 常见企业语料 |
| 代码文件 | 算 | 按语法树切分, 而非按段落 |
| 音频 / 视频 | 算 (间接) | 先转文字稿或摘要描述 |
| Excel 表格 | 算, 但别直接转纯文本 | 行列关系要用 Markdown 表格保留 |
| 图片 | 算 (间接) | 走图像嵌入或让 LLM 生成文字描述 |

**不算的**: 加密且无密钥的文件、解析不出内容的二进制、没有任何语义的纯结构数据。这些不是"格式不支持", 是根本没有可检索的语义。

**工程上的真实边界** (概念边界很宽, 卡点在这三处):

1. **解析能力** - 动态渲染的网页需要无头浏览器; 扫描版 PDF 需要 OCR
2. **访问权限** - 付费墙、内网、需登录的内容技术上可解析但拿不到
3. **清洗后的信噪比** - 正文只占 5%、其余全是模板噪声的页面, 效果会很差

**易混点**: 语料 != 知识库。语料是生料, 知识库是清洗 / 分片 / 建索引后的成品。

### 5.3 清洗与嵌入的分工

常见疑问: "既然 Chroma 不做文本清洗, 那为什么还要嵌入模型?" 这两件事是不同的工序, 缺一不可。

| | 文本清洗 | 嵌入 |
|---|---|---|
| 做什么 | 去噪、结构归一、去重、切块 | 把文本翻译成语义坐标 |
| 谁做 | **使用者自己做** | 嵌入模型做 |
| 为什么 | "什么算噪声"是业务问题, 没有通用答案 | 把"意思相近"变成"坐标相近", 是语义检索的心脏 |

**tokenizer 不算清洗**: 嵌入模型内部的 tokenizer 只是把文字转成编号, 一个字都不会删改。你喂它带满 HTML 标签的脏文本, 它会把标签也编码进向量。

**完整流水线**:

```text
原始文本 -> [清洗] -> [切块] -> [嵌入模型] -> 向量 -> 存储/索引/检索
             你的活    你的活     模型的活           Chroma 的领域
```

**ChromaDB 的内置嵌入**: 有。默认用 `all-MiniLM-L6-v2` (ONNX 本地运行, 384 维), 首次使用需联网下载模型文件。但它是英文为主的模型, 中文场景建议换成 BGE 系列 (如 `BAAI/bge-small-zh-v1.5`)。建库和查询必须使用同一个模型, 中途换模型要重建整个 collection。

**Chroma 不做的**: 文本清洗、去重、切块、超长截断告警。模型有最大 token 限制 (MiniLM 约 256), 超长文本会被**静默截断**, 后面的内容直接丢失且不报错。

### 5.4 固定大小分块: 等长切分 + 块间重叠

两个词拆开看: **等长切分**管"每块多大", **块间重叠**管"相邻块怎么衔接"。

**等长切分**: 定一个目标长度 `chunk_size` (通常是 token 数), 从头往后切。

**块间重叠**: 定一个 `chunk_overlap`, 让下一块从上一块结束前的位置开始, 而不是紧接其后。

```text
Chunk 1: [t1 ----------------------- t500]
Chunk 2:                    [t451 ----------------------- t950]
Chunk 3:                                       [t901 ----- t1000]
                ^ 重叠区 50 token
```

**关键公式**: 实际步进 = `chunk_size` - `chunk_overlap`。上面的例子是 450, 它决定了总共产生多少块。

**为什么要重叠**: 切点附近最容易出事。如果一句关键结论正好横跨切分点, 不重叠的话两块都不完整、语义都受损; 有重叠则两块都能包含完整句子, 至少有一块能命中。**用冗余换边界安全性。**

**"等长"其实是理想化说法**: 真实的固定大小分块 (如 LangChain 的 `CharacterTextSplitter`) 不是机械按字数截断, 而是"段落感知的自适应分块"——先按 `\n\n` 切段, 逐段合并直到超过 `chunk_size` 才收尾。所以实际块长是波动的 (380~520 之间), 只有遇到单个超长段落才会硬切并发出警告。

**最大短板**: 严格等长一定会切在句子中间, 导致 embedding 质量下降。实践中很少单独用它, 而是用递归字符分块改进。

### 5.5 递归字符分块: 分隔符层级递归

核心一句话: **从最粗的边界开始切, 切完还超标就换更细的边界继续, 一路降级直到每块都装得下。**

**分隔符层级** (按颗粒从粗到细):

```text
["\n\n", "\n", "。", "，", " ", ""]
  段落     行     句子    分句   词    字符
```

**递归展开过程**:

```text
按 \n\n 切
|- 片段 A  长度 OK -------------------------- 保留
|- 片段 B  超长
|   |- 按 \n 切
|       |- 还是超长
|           |- 按 。切
|               |- 句子1 + 句子2  合并后 OK --- 保留
|               |- 句子3  超长
|                   |- 按 ，切 -> 按空格切 -> 按字符切 (兜底)
|- 片段 C  长度 OK -------------------------- 保留
```

**四个必须理解的要点**:

1. **递归是局部的** - 只有超标的片段会被送去下一层, 合格的片段当场定稿, 不再被碰
2. **每层留下的叫"片段"不是"句子"** - 按 `\n\n` 切完手里是段落; 按 `。` 切完手里才是句子
3. **分隔符不存在就自动跳过** - 不是"切不出来就放弃", 而是原样返回、直接降到下一级
4. **切完还要合并回去** - 按句号切出 5 句, 不会得到 5 个 chunk, 而是贪心合并到接近 `chunk_size` 为止。**切得细是为了找准边界, 合得粗是为了保住上下文**

**与固定大小分块的关键差异**:

| | 固定大小分块 | 递归字符分块 |
|---|---|---|
| 遇到超长段落 | 保留完整 + 发警告, 可能超出模型上限 | 继续递归降级, 几乎总能切开 |
| 切点位置 | 相对机械 | 尽量落在段落 / 句子边界 |

**实践要点**:

- 中文场景要补上全角标点 (`\uff0c` 全角逗号、`\u3002` 表意句号), 否则用英文标点列表会切不动
- `keep_separator` 默认开启, 切割符保留在相邻片段边界上, 不丢字符
- 它**不知道语义**, 所有判断都基于"长度 + 分隔符", 只是"看起来切得合理"
- 更好的组合是**两阶段**: 先用 `MarkdownHeaderTextSplitter` 按标题切, 再对每块用递归字符细分

### 5.6 语义分块: 按主题边界切分

核心: **不看字数、不看标点, 而是让嵌入模型判断"相邻两句话, 意思还连着吗"——一旦意思突然跳开, 就在那里下刀。**

**直觉: 距离尖峰 = 主题切换**

```text
句子1  如何部署 RAG 系统
句子2  部署步骤包括安装依赖和配置环境      d(1,2) = 0.05   很近
句子3  配置完成后需要启动服务              d(2,3) = 0.08   很近
句子4  今天我们来看看天气预报              d(3,4) = 0.72   <- 尖峰!
句子5  明天北京有小雨                      d(4,5) = 0.10   很近
句子6  后天转晴                            d(5,6) = 0.12   很近
```

前三个距离都在 0.1 以下, 说明是一条连续的语义链; 0.72 处数值突然拔高, 意味着"部署系统"和"天气预报"在向量空间里离得很远。**这就是主题边界。**

**完整五步流程**:

```text
(1) 句子分割      按 。?! 把长文本拆成句子列表
       |
(2) 上下文感知嵌入 不是孤立嵌入单句, 而是把每句和前后各 N 句拼起来再嵌入
       |
(3) 计算相邻距离   每对相邻句子的向量算余弦距离, 得到"距离序列"
       |
(4) 识别断点      用统计方法找出"异常高"的那些距离值
       |
(5) 按断点成块    断点之间的一串句子合并为一个 chunk
```

**第 (4) 步: 四种断点识别方法**

| 方法 | 判断逻辑 | 默认参数 | 特点 |
|---|---|---|---|
| `percentile` | 超过第 N 百分位即断点 | 95 | 默认, 只切最显著的 5% |
| `standard_deviation` | 超过"均值 + N 倍标准差" | 3 | 对分布形状敏感 |
| `interquartile` | 超过 Q3 + N x IQR | 1.5 | 抗极端值, 更稳健 |
| `gradient` | 先算距离变化率, 再对梯度用百分位 | 95 | 适合语义紧密的文档 (法律、医疗) |

**与递归字符分块的本质区别**:

| | 递归字符分块 | 语义分块 |
|---|---|---|
| 判断依据 | 长度 + 分隔符 | 向量距离 |
| 知不知道语义 | 不知道 | 知道 (靠嵌入模型) |
| 切点位置 | 段落 / 句子边界 (形式边界) | 语义突变处 (内容边界) |
| 成本 | 纯字符串处理, 毫秒级 | 要跑一遍 embedding, 慢且花钱 |
| 块大小 | 稳定可控 | **不可控**, 取决于主题长短 |

**关键局限**: 语义分块切出的块可能很大。如果某主题连续讲了 3000 字、中间没有语义跳变, 就会得到一个 3000 字的超级大块, 可能直接超出嵌入模型输入上限。工程上通常要再加一层长度兜底。

**它找的是局部相似度跳变, 不是全局主题结构**:

- 文章在 A / B 主题间反复横跳, 会在每次跳变处切一刀, 切出一堆小碎块
- 一个主题中间插了个不相关例子, 会被切成三块, 人读起来却认为主话题没变

**适用场景**: 长文档、技术白皮书、会议记录、访谈转写 (主题跨度大)。**不适合**: FAQ、短问答、结构清晰的 Markdown。

### 5.7 语义分块内部有递归字符分块吗

**没有。这是两条独立的路线, 依据完全不同** (前者是向量距离, 后者是分隔符 + 长度)。语义分块的五个步骤里, 没有任何一步会去调 `RecursiveCharacterTextSplitter`。

**易误解点**: 第 (1) 步"按 。?! 切句子"看起来像按标点切, 但那只是**一层正则切分**, 目的是得到计算距离的最小单元, 不是逐层降级的递归。

**但长度兜底的问题依然存在**, 这时需要**外挂 (不是内嵌)** 一层:

```text
句子 -> 嵌入 -> 算距离 -> 找断点 -> 成块
                                  |
                        块长度检查: 超标?
                        |- 否 -> 直接输出
                        |- 是 -> 用递归字符分块把这个大块再切细
```

LangChain 的 `SemanticChunker` 默认**不做**这个检查, 这是它的已知短板, 要自己在外面包一层。

**工程上的三种组合方式**:

| 方式 | 做法 | 说明 |
|---|---|---|
| A (最推荐) | 结构分块 -> 语义分块 | 先用标题限定范围, 再在章节内找语义断点 |
| B | 语义分块 -> 递归字符兜底 | 主要目的是控长度上限 |
| C | 纯语义分块 | 只适合中等长度、主题清晰的文档, 生产环境一般不敢裸用 |

**为什么不能真正"融合"**: 两者的断点判据会打架。递归字符分块会在"长度超了"的地方强行下刀, 那个位置可能正好在语义连贯的段落中间, 破坏了语义分块刚刚找到的边界。正确用法是**串行分层**: 语义分块负责理想切法, 递归字符分块负责长度约束, 前者优先、后者兜底。

### 5.8 上下文感知嵌入: buffer_size 在做什么

常见误解: 以为"把 N 个句子合并成一个新句子", 或者以为模型需要"记住 / 判断"这些句子是否语义相同。**都不对。**

**嵌入模型不做任何布尔判断**, 全靠两件事:

```text
1. 把一段 (可能由多句拼成的) 文字 -> 压成一个向量
2. 把两个相邻向量 -> 算一个连续的距离值 (如 0.72)
```

"这里要不要切"是第 (4) 步用统计阈值在全序列上事后算出来的, 不是模型推理时做的判断。

**buffer_size 的实际含义**: 给**每一个句子**单独构造一个带上下文的窗口, 对每个窗口各嵌入一次。`buffer_size = 1` 时:

```text
窗口1 = [S1, S2]              中心是 S1
窗口2 = [S1, S2, S3]          中心是 S2
窗口3 = [S2, S3, S4]          中心是 S3
窗口4 = [S3, S4, S5]          中心是 S4
窗口5 = [S4, S5, S6]          中心是 S5
窗口6 = [S5, S6]              中心是 S6
```

实现上就是**字符串拼接**后丢给嵌入模型, 然后比较**相邻两个窗口的向量**。

**为什么需要它**: 单句嵌入会制造假信号。

```text
S3  配置完成后需要启动服务
S4  然后执行第三步
```

`S4` 单独嵌入时语义残缺 ("第三步"是什么?), 可能给一个反常的向量, 算法误以为换了主题而切一刀。加上 buffer 后 (窗口 = "配置完成后需要启动服务 然后执行第三步 最后验证结果") 语义完整, 距离回归正常。**buffer 的作用是降噪, 不是语义聚合。**

**窗口里的句子不需要语义相同**: 跨边界是正常的, 甚至是必要的。给 S3 配的窗口和给 S4 配的窗口, 内容可以高度重合, 但**服务对象不同**——一个回答"从 S3 往外看是什么语义", 另一个回答"从 S4 往外看是什么语义"。

**代价与权衡**:

```text
buffer_size = 0   纯单句嵌入     噪音多, 容易产生假断点
buffer_size = 1   前后各带一句   默认值, 噪音与边界保留较平衡
buffer_size = 3   前后各带三句   边界被抹得厉害, 真实切换可能测不出来
```

**重要推论**: 相邻窗口共享 2/3 内容, 向量天生相似, **所有距离值被整体压低**。所以不能用绝对阈值 (如"距离 > 0.5 就切"), 必须用**相对比较**——这正是默认用 `percentile` 百分位法的根本原因。

### 5.9 "上下文窗口"的两种含义 (同名不同义)

这里和 LLM 的上下文窗口**同名不同义**, 必须先剥掉这层混淆。

| | LLM 的上下文窗口 | 语义分块里的上下文窗口 |
|---|---|---|
| 指什么 | 一次能接收的 token 容量上限 (8K、128K) | 给某句算向量时**人为圈定的邻居句子范围** |
| 单位 | token | 句子 (通常 2N+1 句) |
| 谁定的 | 模型架构 | `buffer_size` 参数 |
| 作用 | 限制"能塞多少内容进去" | 决定"这句话带多少邻居一起被理解" |
| 超了会怎样 | 截断或报错 | 窗口变宽, 距离被平滑得更厉害 |

前一个是**容量限制**, 后一个是**观察范围**。

**具体定义**: 对第 `i` 句, 窗口 = 以它为中心、前后各取 N 句拼成的一小段文字。

```text
窗口_i = 句子[i-N] + ... + 句子[i-1] + 句子[i] + 句子[i+1] + ... + 句子[i+N]
                     ^ 前文               ^ 中心            ^ 后文
```

**"滑动"是本质特征**: 给下一句配窗口时整体往右挪一格, 左边掉出一句、右边补进一句。

**为什么中心句需要它**: 单看一句话意思可能不完整。"然后执行第三步"单独看不知所指, 带上前后文才语义完整——和人类阅读时回看前文理解指代词是同一个直觉。

**边界细节**: 首尾两句的窗口不对称。`S1` 的窗口只有 `[S1, S2]`, 前文缺失。文本很短时这个效应比较明显。

**"各嵌入一次"的代价**: 不是整篇嵌入一次, 而是 **1000 句话 -> 1000 个窗口 -> 1000 次嵌入调用**。这是语义分块比递归字符分块慢得多、贵得多的根本原因。

### 5.10 窗口向量 v_i 该怎么理解

**它包含前后文, 但是融合式的, 不是并置式的**:

```text
W3 = [S2, S3, S4]                     <- 先把三句话拼成一个字符串
        |
v3 = [0.12, -0.34, 0.56, ..., 0.78]   <- 得到一个 1024 维向量
```

```text
x 不是: v3 = [S2 的向量] + [S3 的向量] + [S4 的向量]   (三个向量拼起来, 3072 维)
v 而是: v3 = encode("S2 S3 S4")                        (一个向量, 1024 维)
```

三句话的信息在池化层被压成一个向量, **无法从里面把 S2 的部分单独抠出来**。

**更准确的叫法**: 不是"句子向量", 而是 **"窗口向量"** 或 **"第 i 句在上下文中的向量"**。它回答的不是"第 i 句是什么意思", 而是"第 i 句周围那一片区域整体是什么语义"。

**关键细节: 中心句没有被加权**。这点极易误解——既然叫"给 S3 配的窗口", 直觉上以为 S3 权重更高, 但实现上就是纯字符串拼接后照常嵌入, 池化时对所有 token 求平均, 没有任何机制给中心句加权重。如果 S2 或 S4 比 S3 长很多, 它们的 token 更多, 影响反而**超过** S3。

"中心"只是**组织上的命名**——标记这个窗口为哪句话服务、这个向量挂在哪个句子位置上, 不是数学上的特权位置。想通这点, 对"边界会被模糊"就自然理解了。

**怎么用这些向量: 看"掉出的"和"进来的"**:

```text
W3 = [ S2   S3   S4 ]
W4 =      [ S3   S4   S5 ]
       ^            ^
     S2 掉出      S5 进入
       +-- 共同部分 S3 S4 --+
```

`W4` 相比 `W3` 只做了一件事: 左边掉出一句, 右边补进一句, 共同部分基本抵消。所以:

```text
distance(v3, v4)  ~=  反映 "S2 和 S5 的语义差异"
```

**一个真实的主题边界会在连续三对相邻窗口上表现为"抬高的距离"**, 而不是孤立尖峰:

```text
d(v2, v3)   S1(A) 掉出, S4(B) 进来   -> 距离升高
d(v3, v4)   S2(A) 掉出, S5(B) 进来   -> 距离升高
d(v4, v5)   S3(A) 掉出, S6(B) 进来   -> 距离升高
d(v5, v6)   S4(B) 掉出, S7(B) 进来   -> 回落
```

边界没有被抹掉, 只是从"一个尖峰"变成了"一段高原"。

**一句话总结**: `v_i` 是"从第 i 句往外看 N 句"这一整片区域的语义快照。它包含前后文, 但前后文与中心句的贡献混在一起无法拆开。比较 `v_i` 和 `v_{i+1}`, 问的是"观察窗口往右滑一格, 语义变了多少"。
