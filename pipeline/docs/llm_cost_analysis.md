# 当前 RAG 栈的 LLM 成本分析

日期：2026-09-20
地域：阿里云百炼 **华北2（北京）**，CNY 原价（不含限时优惠）
栈：`qwen3.7-text-embedding` + `qwen3.7-text-rerank` + `qwen-turbo`

> **一句话结论**：单次问答约 **0.0041 元（4.1 毫元）**。其中 **84% 花在 rerank**，
> 生成只占 15.6%。**唯一有实质效果的省钱杠杆是把 rerank 候选数从 20 砍到 10（省 42%）**；
> embedding 降档几乎没用（query 只占 0.5%），生成换模型反而更贵（turbo 已是最便宜档）。

## 三、单次查询成本分解（核心）

### token 估算依据（全部取自代码默认值，非臆测）

| 来源 | 参数 |
|---|---|
| `rag_server.py` | `candidate_k=20`、`rerank_candidate_k=20`、`context_k=5`、`max_context_chars=6000`、`max_tokens=800` |
| `reranker.py` | `max_doc_chars=4000` → 单条 342.5 tok **未触发截断** |
| `generation.py` | system prompt ≈ 120 tok，user 模板 ≈ 30 tok，query ≈ 40 tok |

### 分解表

| 环节 | 输入 token | 输出 token | 成本（毫元） | 占比 |
|---|---|---|---|---|
| query embedding（1 条） | 40 | — | 0.0200 | 0.5% |
| **rerank（20 条候选）** | **6,889** | — | **3.4447** | **84.0%** |
| 生成（上下文 6,000 字符 ≈ 1,130 tok） | 1,320 | 400 | 0.6360 | 15.6% |
| **合计** | | | **4.101 毫元** | 100% |

**单次查询 ≈ 0.0041 元**

> rerank 的 6,889 token = 20 条候选 × 342.5 tok + query 40 tok。
> 这是每问一次都要付的**固定大头**，与答案长短无关。

### 敏感性（结论稳健）

| chars/token | 答案输出 | 单次成本 |
|---|---|---|
| 4.5 | 200 tok | 4.04 毫元 |
| **5.31（实测）** | **400 tok** | **4.10 毫元** |
| 6.0 | 800 tok（= `max_tokens` 上限） | 4.30 毫元 |

即使把"答案输出"从 400 拉到 800 的硬上限，成本也只从 4.10 涨到 4.34 毫元（+6%）。
**rerank 主导这一点不受估算假设影响。**

## 四、规模化外推

| 规模 | 成本 |
|---|---|
| 1 次 | 0.0041 元 |
| 1,000 次 | **4.10 元** |
| 10 万次 | **410 元** |
| 100 万次 | **4,101 元** |

**参照**：一个月 10 万次查询 ≈ **410 元**，约合 $57。这个量级下，
LLM 推理成本通常**低于**向量库 + 服务器的固定开销 —— 不要为省钱牺牲检索质量。

## 五、建索引一次性成本（可忽略）

| 场景 | token | 成本 |
|---|---|---|
| 全量重建（10 篇 / 117 chunks） | 40,069 | **0.020 元** |
| 增量一篇（avg） | 4,007 | 0.002 元 |

→ 重建索引 25 次才花 0.5 元。**成本几乎 100% 来自线上查询，不在建库。**

## 六、免费额度覆盖倍数

| 模型 | 免费额度 | 可覆盖 |
|---|---|---|
| embedding | 1M token | **25 次全量重建** |
| **rerank** | 1M token | **145 次查询** ← 瓶颈 |
| chat 输入 | 1M token | 758 次查询 |
| chat 输出 | 1M token | 2,500 次查询 |

→ **rerank 是免费额度最先耗尽的模型（145 次查询）**。
这正好解释了评估阶段实测到的 `403 AllocationQuota.FreeTierOnly`：
把 `candidate_k` 开到 100 时，单次查询就要 rerank 100 条 ≈ 34K token，
39 条 qrels × 多轮扫描几轮就把 100 万额度烧穿了。

**对开发的含义**：评估阶段先跑 dense/rrf 阶段（不花钱），
只在最终确认时才开 rerank 阶段，避免把免费额度浪费在参数扫描上。

## 七、优化杠杆（量化）

| 方案 | 单次成本 | 节省 | 评价 |
|---|---|---|---|
| 基线 | 4.101 毫元 | — | |
| A. embedding 降档 `-flash` | 4.086 毫元 | 0.4% | ❌ query 只占 0.5%，改了等于没改 |
| **B. rerank 候选 20 → 10** | **2.388 毫元** | **41.8%** | ✅ 唯一有实质效果的杠杆 |
| C. 生成换 flash 档 | 5.092 毫元 | **−24%（更贵）** | ❌ turbo 已是最便宜档，升档反而涨 |
| D. A + B 组合 | 2.373 毫元 | 42.1% | 与 B 基本相同，A 是噪音 |

### 关键洞察

1. **省钱只有一个方向：砍 rerank 候选数。** 20 → 10 省 42%。
   佐证：实测 `candidate_k=20` 时 rerank 的 hit@5 与 recall@20 都已是 **1.000**，
   rrf 阶段 recall@20 也已是 1.000 —— **候选池本身有冗余，砍到 10 有空间**。
   但必须重跑评估确认不掉点（当前 k=50 时 rerank hit@5 掉到 0.941，说明并非单调安全）。
2. **embedding 降档是无用杠杆**：单次查询的 query 向量只占 0.5% 成本。
   只有当**建库量极大**时才值得考虑 flash 档（省 0.05 元/百万 token）。
3. **生成侧没有优化空间**：`qwen-turbo` 就是最便宜的可选档；换 flash/plus 只会更贵。
   生成总占比 15.6%，即使完全免费也只省 15.6%。
4. **Batch 半价对 rerank 不可用**：`qwen3.7-text-rerank` 官方标记**不支持批量推理**，
   所以"离线跑一半价"这条路在 rerank 上走不通 —— 而 rerank 恰恰是大头。
5. **上下文缓存也帮不上**：`qwen3.7-text-rerank` 不支持上下文缓存。

## 八、估算假设与局限

| 假设 | 说明 |
|---|---|
| chars/token = 5.31 | 由 212,858 字符 / 40,069 token 实测得出，仅用于把 `max_context_chars=6000` 换算成 token |
| 答案输出 400 tok | 经验值；`max_tokens=800` 是上限而非实际值。对结论影响 ≤6% |
| 20 条候选平均 342.5 tok | 用全库均值代替实际候选；未触发 `max_doc_chars=4000` 截断 |
| 未计上下文缓存/限时优惠 | 一律按原价；实际账单可能更低 |

**如何得到精确账单**：`reranker.py` 与 `generation.py` 目前**丢弃了响应体的 `usage` 字段**
（rerank 返回 `usage.prompt_tokens`/`total_tokens`，chat 返回 `usage.prompt_tokens`/`completion_tokens`）。
若要把估算换成实测计费，最小改动是在两处把 usage 落盘累加。
本次**不做**该改动 —— 列为后续可选。

---

## 九、结论

1. 单次问答 **0.0041 元**；10 万次 **410 元**。
2. **rerank 占 84%**，是唯一值得优化的环节；生成占 15.6% 且已最便宜。
3. 免费额度瓶颈也是 rerank（145 次查询），与实测的 403 现象一致。
4. 建索引成本 0.02 元/次全量重建，可忽略。
5. 若要压成本：**先评估 candidate_k=10 是否掉点**；否则维持现状即可 ——
   这个成本量级下，检索质量远比省几毛钱重要。
